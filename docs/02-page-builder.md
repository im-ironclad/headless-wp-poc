# The Page Builder, end to end

We follow **one Block Type (Hero)** through every layer. Every other Block Type works the same way.

## 1. Definition: SCF → Field Groups → Page Builder

Built in the wp-admin UI (on a local site). SCF writes every save to **Local JSON**:
`wordpress/web/wp-content/themes/headless/acf-json/group_page_builder.json`, which is committed.

```jsonc
{
  "key": "group_page_builder",
  "fields": [{
    "key": "field_pb_blocks", "name": "blocks", "type": "flexible_content",
    "layouts": {
      "layout_hero": { "name": "hero", "label": "Hero", "sub_fields": [
        { "key": "field_hero_heading", "name": "heading", "type": "text", "required": 1 },
        { "key": "field_hero_image",   "name": "image",   "type": "image" },
        { "key": "field_hero_cta",     "name": "cta",     "type": "link" }, …
  ]}}}],
  "location": [[{ "param": "post_type", "operator": "==", "value": "page" }]],
  "show_in_graphql": 1,
  "graphql_field_name": "pageBuilder",
  "modified": 1790823245
}
```

- **Local JSON workflow (the usual agency setup).** Edit the field group in SCF locally → SCF rewrites the JSON → commit it. On another environment, SCF reads the JSON on every request (so the fields work straight away), and shows **Sync available** to import it into that database. `setup.sh` does that import with `sync-acf-json.php`. The SCF admin is hidden outside `local` (`headless-config.php`) so nobody edits the schema on production, where the change would be overwritten by the next deploy.
- **The alternative: PHP registration** (`acf_add_local_field_group([...])` in a plugin). It's fully code-reviewed and can be generated programmatically, but the groups never appear in SCF → Field Groups, which confuses editors and anyone exploring wp-admin. Agencies use it for fields that are built in code (e.g. shared field sets reused across plugins).
- `key`s must be globally unique and never change. ACF stores them next to every value. Changing a `name` orphans existing content.
- `show_in_graphql` + `graphql_field_name` (the **GraphQL** tab in the field group settings) are the only things WPGraphQL for ACF needs.
- The **Site Settings** Options Page is Local JSON too (`ui_options_page_site_settings.json`), listed under SCF → Options Pages.

## 2. Editing: wp-admin → Pages → Home

The editor sees a **Blocks** field with **Add Block**. Each Block is a collapsible panel that can be dragged to reorder, duplicated or removed. That's the whole editing experience, the same as Matrix. Gutenberg is turned off for Pages (`headless-config.php`) so editors only see this one way of building a page.

## 3. Storage

```
blocks            = a:5:{i:0;s:4:"hero";i:1;s:9:"rich_text";…}   ← order + Layout per row
blocks_0_heading  = "Websites that move at the speed of your ideas"
blocks_0_image    = 8                                            ← attachment ID
blocks_0_cta      = a:3:{s:5:"title";…}
```

Reordering only rewrites these meta rows. The Page itself doesn't change.

## 4. GraphQL schema (generated by WPGraphQL for ACF)

```graphql
type Page { pageBuilder: PageBuilder }
type PageBuilder { blocks: [PageBuilderBlocks_Layout] }   # interface, one implementation per Layout
type PageBuilderBlocksHeroLayout implements PageBuilderBlocks_Layout {
  heading: String
  subheading: String
  image: AcfMediaItemConnectionEdge   # → image { node { sourceUrl altText mediaDetails { width height } } }
  cta: AcfLink                         # → { title url target }
}
```

Naming rule: `{GroupGraphqlName}{FieldName}{LayoutName}Layout`. Two quirks the Adapter handles:
- **Select fields return a list** (`imagePosition: ["right"]`), even for a single select.
- **Images are connection edges**, so you have to go through `node`.

Try it in wp-admin → GraphQL → GraphiQL IDE:

```graphql
{ page(id: "/", idType: URI) { title pageBuilder { blocks { __typename ... on PageBuilderBlocksHeroLayout { heading } } } } }
```

## 5. Query: `web/src/lib/cms/wordpress/fragments/blocks.ts`

One fragment per Layout, combined with inline fragments on the `__typename` union:

```ts
export const HERO = `fragment Hero on PageBuilderBlocksHeroLayout {
  heading subheading image { ...ImageFields } cta { ...LinkFields } }`;
// PAGE_BUILDER: pageBuilder { blocks { __typename ...Hero ...RichText ...FeatureGrid ... } }
```

## 6. Adapter: `web/src/lib/cms/wordpress/adapter.ts`

```ts
case "PageBuilderBlocksHeroLayout":
  if (!str(layout.heading)) return "invalid";
  return { type: "hero", id, heading: …, image: toImage(layout.image), cta: toLink(layout.cta, ctx) };
default:
  return "unknown-type";
```

The WordPress-specific shape becomes a `HeroBlock` from `lib/cms/types.ts`. Along the way, the Adapter:
- rewrites WordPress URLs to relative paths (`https://headless-wp.ddev.site/about/` → `/about`)
- sanitizes rich text
- keeps editor order
- turns unknown or incomplete Layouts into an **Unsupported Block** instead of failing the Page

## 7. Render: `web/src/components/blocks/block-renderer.tsx`

```tsx
const components = { hero: Hero, richText: RichText, … } satisfies { [T in BlockType]: … };
blocks.map((block) => <Component key={block.id} {...block} />)
```

`satisfies` means TypeScript fails the build if a Block Type has no component. Unsupported Blocks render nothing in production, and a dashed placeholder in dev and Draft Preview.

## Adding a new Block Type (checklist)

1. **SCF (local):** add a Layout to the Page Builder field group and commit the updated `acf-json/group_page_builder.json`.
2. **Types:** add `XBlock` to the `ContentBlock` union in `lib/cms/types.ts`.
3. **Query:** add a fragment in `fragments/blocks.ts` and spread it in `PAGE_BUILDER`.
4. **Adapter:** add a `case` (test first in `adapter.test.ts`).
5. **Component:** add `components/blocks/x.tsx` and register it in `BlockRenderer`. TypeScript will remind you.
6. **Contract:** re-run `yarn test:contract`.

Deploy order doesn't matter. If WordPress ships the Layout first, editors can use it, and it stays hidden on the live site until the frontend ships.
